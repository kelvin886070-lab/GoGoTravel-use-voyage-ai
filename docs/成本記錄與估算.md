## 2. 目前的成本護欄（已在，2026-07）

- **每人每日 200 次 Google 呼叫硬限額**（搜尋＋geocode 共用；`geocode_usage` 表）。滿了回空、不再打 Google → **單一使用者一天花費有硬天花板**。
- **全域快取**：`cached_locations`（geocode/findplace）、`cached_searches`（搜尋，TTL 7 天）。快取命中＝免費、不計數。
- **前端**：debounce 0.35 秒、至少 2 字才查、第一頁快取。
- **分頁封頂**：Places 一個關鍵字約 3 頁 / 60 筆，token 撈完就停 → 「更多結果」不可能無限點。

## 3. 待加護欄（成本升高時再上；對應 §11 規模化清單）

- [ ] **搜尋獨立每日額度**（與 geocode 分流，單獨鎖搜尋花費、不餓死地理編碼）。
- [ ] **分頁結果也快取**（現在只快取第一頁；同關鍵字重複「更多結果」→ 免費）。
- [ ] **預算 guard／爆量告警**（花費接近門檻通知）。
- [ ] **搜尋結果照片/營業時間欄位** 會提高 Places SKU → 加時記成本。
- [ ] **免費層每日上限 ＋ 付費層放寬**（商業模式對齊：重度搜尋＝高意圖＝付費甜蜜點）。
- [ ] **「更多結果」點按次數上限**（實測可按 >5 次＝分頁比預期鬆，每次都打一次 API）。目前仍受每日 200 硬限額擋著，但可加「單次搜尋最多載入 N 頁」再省。Kelvin：D2.3 後決定。
- [ ] **評分/營業時間欄位＝Places SKU 升級（重要成本點）**：加 `rating` → Enterprise SKU；加 `openingHours` → Enterprise+Atmosphere SKU（**最貴**）。每筆搜尋結果都帶＝成本明顯上升。
  - **【D2 評分 定案・方案A】** 評分**只在「存進清單／開地點細節」時查一次** Place Details（帶 `rating`/`userRatingCount`），**不在搜尋列表每筆帶** → 由 O(結果數) 降為 O(1)。顯示位置：**地點細節卡 ＋ 清單項目**。要加：(1) 評分查詢納入每日 200 硬限額（與搜尋/geocode 共用計數）；(2) rating 結果快取（同 placeId 不重複打）；(3) 用量進下方 §4 記錄。營業把關同樣「選定時查 Details 一次」，不每筆帶 openingHours（避 Atmosphere 最貴 SKU）。
- [ ] **貼連結（D2）**：優先純解析 URL 抽座標（免費），抽不到才 fallback 一次 resolve；重用 `cached_locations`。低成本，但仍受每日 200 硬限額保護。

## 3.7 回憶照片（批⑤c · 旅程相簿）
- **儲存**：壓縮後 ~250–400KB/張；上限＝一律 150 張/趟（規則單純好溝通；天花板不變） → 極端 ~45MB/趟。Supabase 免費層 1GB storage——自用無虞；**規模化前要重評**（10 使用者 × 3 趟 × 45MB ≈ 1.35GB 即破免費層）。
- **Egress（真炸點）**：播放膠卷＝重載大圖，重複觀看吃 egress（先前已撞過 5GB 上限）。**✅ 縮圖層已做（2026-07-31 效能量測批）**：上傳雙檔（原圖＋~480px/0.72 影子縮圖 `uuid_t.jpg`，命名衍生不動 schema）；膠卷漸進式＝縮圖立即上畫、停留 400ms 才抓當前格大圖（連翻不下載大圖）；舊照無縮圖自動退回大圖。量測依據：iPhone 真機 profile，大圖首次上畫＝解碼 400~1100ms（膠卷頓的真兇）、翻頁引擎本身 60fps 無罪。**✅ 封面縮圖也已做（同日封面縮圖小批；test-05 量測翻回憶頁 390~580ms 慢幀＝封面 1200px 首次解碼）**：回憶卡 208px 改用小圖——自家封面上傳走影子縮圖管線（uploadTripImageWithThumb，兩處封面上傳入口都換）、Pexels 封面 URL 參數直接要 640×350（CDN 即時縮放，零 API）；舊封面無影子檔退回大圖（要受益需重新上傳封面或未來回填批）。
- **精選膠卷**（記錄待辦）：相簿（倉庫，最多 150）≠ 膠卷（精選 15–24 張，`memoryReelPaths` 子集）；選片 UI 獨立小批。精選同時也是 egress 護欄（預設只播精選）。

## 3.8 目的地情報（destination-intel · 生成表單重設計的資料管線）
- **一次呼叫餵四頁**：顆粒度判定（縮圈要不要出現／打錯猜測）＋地帶卡組＋玩法標籤＋各月季節註記＋順遊城市＋國家 ISO（國內外推斷）＋cityEn（封面照片沿用）＋幣別（旁註）。用 Gemini flash-lite，單次輸出 ~1–2KB。
- **三層省錢護欄**：①**全域快取 35 天**（Kelvin 定案：避免換季過季詞條）（`cached_destination_intel`，**同一查詢字串全體使用者共用一筆** → 「日本」全世界只算一次，第二次起零 LLM 成本）②前端快取 7 天＋同查詢併發去重（表單來回上一步不重打）③**<2 字元前後端都不打**；未命中才 `bumpDailyOrLimit`（共用每日 200 硬限額，防亂字串刷 API）。
- 預期用量級別：新目的地才產生成本；台日韓等高頻目的地上線首週即全快取。unknown（打錯字）也存快取——同一個錯字不會反覆打 LLM。
- ❗待辦：長尾國家的 LLM 品質需 Kelvin 抽查（docs E3 已記「高頻國家先開」）；快取表若需清洗（模型換版/內容改規格）＝直接 `delete from cached_destination_intel`，下次查詢自動重建。

### 3.8.1 亂填防線帶來的成本效果（2026-08-04 亂填批）
- **第四道護欄：本地啟發式（`services/placeSanity.ts`，零成本純函式）**——明顯亂打的字串（鍵盤連打、同字元連 3 次、純數字/標點、無母音、5 連子音、罕用子音相鄰、CJK 超過 12 字、公認測試字串完全相符）**在前端就攔下，一次 LLM 呼叫都不發**。這是唯一「越多人亂打越省錢」的護欄：舊路徑是亂碼也照打 LLM、照寫快取表（一列垃圾佔一列成本）。
- **連帶省下 Pexels 封面照呼叫**：未通過驗證的目的地**不抓封面照**（`isVerifiedIntel` 為假就直接 return）——亂填不再各燒一次照片 API。
- 規則刻意保守（寧可少抓不錯抓），已對 Szczecin／Berlin／Cwmbrân／Ljubljana／Rzeszów／Qingdao 等真實地名做過反例測試；已知並接受的偽陽性只有 `Jwaneng`（波札那小鎮，代價僅虛線圈＋一次確認）。
- 未採用的方案與理由：**Google Places 交叉驗證雖最準，但每個目的地都驗會直接推高變動成本**——現階段不做，除非實測 LLM 誤判造成實害（記在此以免日後重複討論）。

### 3.8.2 情報拆成兩層（2026-08-04 延遲批；**成本與延遲同時改善**）
- **病灶**：一顆 `destination-intel` 要模型一次生出 6–8 組地帶卡＋8–10 標籤＋**12 個月季節註記**，`maxOutputTokens` 還開到 8192。**輸出長度＝生成時間**，實測入口頁等超過兩分鐘——等的是三頁之後才用得到的資料。
- **修法**：拆成 **輕層 `destination-intel`**（顆粒度/正規名/國碼/cityEn/幣別/順遊/猜測，≈200 token，`maxOutputTokens: 512`，**入口頁只等這層**）與 **重層 `destination-deep`**（地帶/標籤/季節，`maxOutputTokens: 4096`），重層由前端在目的地驗證通過後**背景預取**（`prefetchDestinationDeep`），使用者填完後面幾頁走到縮圈頁時通常已在快取。
- **總 token 反而更少**：城市級目的地根本不需要地帶卡，舊版每次照生；現在只有真的會用到才生。
- **每日限額計數**：新目的地從 1 次變 2 次（輕＋重），但**只在快取未命中時**；重層失敗完全不影響主流程（有通用組退位）。
- **逾時護欄（新）**：`geminiText` 加 AbortController——預設 120s（行程生成本來就長，這是最後安全網）、輕層 12s、重層 45s；前端另有 8s 硬上限。日誌加 `ms` 欄位，**延遲從此可量測，不必再靠猜**。
- ⚠️ 給未來的自己：`maxOutputTokens` 不是「保險起見開大一點」的參數，**它就是最壞情況的等待時間上限**。

### 3.8.3 重層加 `budget` 欄位（2026-08-09 ⑥想怎麼玩頁・預算錨點）
- **變動**：`destination-deep` 的輸出多一段 `budget: { lean, mid, rich }`（三個字串區間，一律**不含機票住宿**）。輸出**約 +60 token**。
- **為什麼幾乎沒有成本**：加在**現有的重層呼叫裡**，不是第三顆呼叫——**零額外 API 呼叫、零額外快取表、每日限額計數不變**。重層是背景預取，也不影響任何等待時間。
  ⚠️ 若當初做成「另外問一次預算」，代價會是：多一次 LLM 費用＋多一份快取要維護＋多一個會失敗的地方，而換到的東西是零。**同一顆呼叫多帶一個欄位，永遠優於多開一顆呼叫。**
- **一次性成本**：`kt_dest_deep_v3` → v4，伺服器端 `deep:` 舊資料清空重生（**Kelvin 選「清掉重問」**，2026-08-09 僅 3 筆，成本 < NT$1，可忽略）。
  ```sql
  delete from public.cached_destination_intel where query like 'deep:%';   -- 只刪 deep:，輕層格式沒變
  ```
  ⚠️ 前端仍**必須對缺 `budget` 退位**（不顯示錨點那一行）——未來若使用者變多、快取列數變大，就會改採「不清快取、讓舊資料在 35 天內自然汰換」的零成本路徑。退位邏輯是那條路徑的前提。
- **不入 prompt 的成本意義**：這些金額**不會被送回生成行程的 prompt**（見產品筆記 §1 原則 14）——所以它不會推高行程生成那顆（最貴的）呼叫的輸入 token。

### 3.10 🔴 「整理一下」（refine-notes）— **整條管線第一個「零快取」的呼叫**
- **⑦你的講究**頁的手寫欄，使用者按「整理一下」＝把口語整理成條列。
- 🔴 **內容因人而異，快取不可能命中**——**每按一次就是一次真實花費**。這與目的地情報的成本模型完全不同（那些是「全世界第一個人付錢，之後 35 天免費」）。
- 規格：`maxOutputTokens: 700`、`timeoutMs: 20s`、輸入上限 400 字（前端 200，Edge 端再擋一次）。單次約 300–600 token。
- **護欄現況**：只計入每日限額（`bumpDailyOrLimit`）。
  ⚠️ **次數上限（Kelvin：每份 brief 最多 3 次）驗收後才開啟**——`NotesPage` 的 `TIDY_LIMIT` 目前是 `Infinity`，**改成 3 就上線，其餘程式一行都不用動**。
  與「生成品質驗收批」同一個原則：**沒有量測就不要先加限制**，可能在解決一個不存在的問題。
- prompt 的核心約束是「**絕對不可以新增旅客沒說的偏好**」——那是整理器最容易犯的錯（自作主張補上「還想看夜景」），而它會直接污染行程。

### 3.9 模型切換比較（Gemini vs Claude）— 待做，**表單完成後的第一批**
- **為什麼要比**：Kelvin 舊版實測「選了緊湊，生成出來一天只有兩個景點」＝**硬約束被無聲忽略**。這不只是品質問題，它讓表單所有的度量衡副標變成裝飾。
- 🔴 **不能只比單價。三個維度一起看**：①**指令遵守率**（每日站數／抵達離開時間／預算指令／負面約束的違規率）②每次生成的**實際 token 與費用** ③**延遲**。
  ➜ **便宜但常違規的模型，真實成本要算上重試與使用者流失。**
- **前提：先有輸出驗證器才有得比**（見產品筆記 E3-0「生成品質驗收批」）——**沒有量測就沒有比較**。
  第一步只做「記錄違規項」，不要急著加重試（重試＝成本直接翻倍）；跑十趟看違規率再決定。
- **切換成本很低**：`ai-proxy` 已經把模型包在後面（前端完全不知道背後是誰），換模型只改一個檔案的一個字串。

## 4.5 💰 2026-08-14 每日限額改版：等權計數 → 加權點數（資安批）

- 舊制：所有 action 每次 +1、共用 200/日。問題：一次 Gemini 行程生成（6144 token 輸出）與一次
  Geocoding（$5/1000）等權——**200 次上限實質上是「200 次最貴呼叫」的上限**。
- 新制：`ACTION_COST` 加權（gemini-text 5／vision 8／deep 5／intel·refine 2／Maps 系與其他 1），
  預算 `DAILY_BUDGET = 200` 點/人/日；快取命中不扣點（既有設計不變）。
- 計數改走 `bump_usage` 原子 RPC（`supabase/usage_rpc.sql`）——舊的讀寫兩步在並發下會少算。
- 換算感：一天 200 點 ≈ 40 次行程生成、或 25 次影像辨識、或 200 次地圖查詢的**混合**。
  正常單人使用遠碰不到；碰到的是腳本。權重與預算日後依 §4 實際帳單校準。
