### 但下面這條鏈是真的，而且報告沒寫

## ② P1-1：SSRF 成立，但「會導致 service role key 外洩」未成立

程式碼與報告引用**完全一致**，四層問題全部屬實。有爭議的是排名理由：

> 「這是全清單中唯一有可能導致 service role key 外洩的路徑」

不成立的理由：

1. **SSRF 不讀環境變數。** 它讓伺服器發請求，不讓攻擊者讀 `Deno.env`。
2. **這個 fetch 不帶任何憑證**——沒有 Authorization、沒有 apikey。打到 Supabase 內部端點也是未授權身分。
3. **回傳極窄**：只有 `coords` 與 `finalUrl`，`body` 只餵給 `coordsFromString`（找 `@lat,lng` 樣式），不外流。
4. Deno Deploy 是 isolate 環境，**沒有 AWS IMDS 那種會吐憑證的 metadata endpoint**。

真實嚴重度：**帶 `finalUrl` oracle 的內網/外網探測 ＋ 把你的 Edge Function 當匿名代理與流量放大器**。
仍要修，但它不該把 P1-3（10 分鐘、直接止血）擋在後面。

### 反問

報告問對了一半。更該問的是：

> `coordsFromString` 已經在做字串解析，`res.text()` 那一步是為了處理哪一種**真實遇過**的短網址？

這條路走通的話，P1-1 不是「加白名單」，是**整段刪掉一半**。

# 報告沒抓到的兩個問題

## 🟠 新-1　vault 檔名熵不足，且兩處寫法不一致

```ts
// VaultView.tsx:151-153  ← 保管箱主上傳
const safeFileName = `${Date.now()}_${Math.random().toString(36).substring(7)}.${fileExt}`;

// bookingFile.ts:10      ← 訂位檔上傳
const path = `${user.id}/bookings/${crypto.randomUUID()}.${ext}`;
```

`Math.random().toString(36).substring(7)` 約 6 碼 base36（≈31 bit），且 `Math.random()`
**不是密碼學安全的**——V8 用 xorshift128+，觀察到同一 session 的少量輸出即可還原內部狀態、
推算前後值。`Date.now()` 又幾乎可猜。相較之下 `crypto.randomUUID()` 是 122 bit。

**在 private bucket ＋ RLS 之下這不構成漏洞**（路徑猜中也讀不到）。
它的意義是**縱深**：P0-1 的情境正是「RLS 失效時，路徑本身還剩多少保護」。
報告問了「路徑可不可猜」卻沒去看程式碼——答案是「比它以為的好猜」。

→ 統一改用 `crypto.randomUUID()`。舊檔不必遷移（路徑存在 DB，改了要一起改）。

## 🟠 新-2　前端沒有影像大小上限

`BookingImportSheet.onPickFile` 直接 `readAsDataURL` 就送。
30MB 的手機照片 → base64 後約 40MB → 打進 Edge Function。
`VaultView` 有 `file.size > 10MB` 的檢查，匯入這條路**沒有**。

→ 客戶端先擋（並考慮壓到長邊 1600px：OCR 用不到原始解析度，成本與延遲同時降）。
這比 P1-5 的伺服端檢查更該先做——**送出去才發現太大，錢已經花了**。
