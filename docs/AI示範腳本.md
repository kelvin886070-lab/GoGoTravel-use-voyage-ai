# 🎬 Kelvin Trip・AI 與資料流示範腳本

> 給 Kelvin 向夥伴展示「我們的 LLM 是怎麼運作的、資料怎麼變、資料庫怎麼變」用。
> 全程約 8–10 分鐘。**不要即興**——照這個順序走，每一幕都有一個要讓對方記住的重點。

---

## 0. 事前準備（自己先做，約 3 分鐘）

**開四個視窗，排成兩兩並列：**

| # | 視窗 | 網址／位置 |
|---|---|---|
| A | App（手機或瀏覽器） | 你的 PWA |
| B | Edge Function 日誌 | Supabase → Edge Functions → `ai-proxy` → Logs |
| C | 資料庫 | Supabase → Table Editor → `cached_destination_intel` |
| D | 瀏覽器 DevTools | Network 分頁，篩選 `ai-proxy` |

**把快取清乾淨**（讓第一幕能演出「冷啟」）：

```sql
-- Supabase SQL Editor
delete from public.cached_destination_intel where query in ('日本', 'deep:日本');
```

```js
// DevTools Console（清前端快取）
Object.keys(localStorage).filter(k => k.startsWith('kt_dest')).forEach(k => localStorage.removeItem(k));
```

⚠️ **不要開啟的畫面**：Supabase → Edge Functions → **Secrets**（那裡有 GEMINI_KEY）。示範時螢幕分享很容易誤入。

## 第一幕・冷啟：一句話變成結構化資料（2 分鐘）

**操作**：在 App 輸入「日本」，按加入。

**依序指給對方看：**

1. **視窗 D（Network）**：只有**一個**請求 `ai-proxy`。點開 Payload——
   > 「你看,前端送出去的只有 `{action: 'destination-intel', payload: {query: '日本'}}`。
   > **沒有任何 API 金鑰**。金鑰只存在 Supabase 的伺服器環境變數裡,任何人打開瀏覽器的開發者工具都拿不到。」

2. **視窗 B（日誌）**：出現 `[destination-intel] ok { query: "日本", g: "country", ms: 929, len: 218 }`
   > 「929 毫秒。這是**輕層**——它只回答一件事:這是不是一個真的地方、屬於哪個國家。
   > 我刻意讓它很小,因為使用者正在螢幕前面等它。」

3. **視窗 C（資料庫）**：重新整理 → 多出一列 `日本`。點開 `data` 欄看 JSON。
   > 「一句『日本』被變成了結構化資料:顆粒度、國碼、幣別、代表城市、順遊城市。
   > 這些欄位之後會餵給行程生成的 prompt。」

**要對方記住的一句話**：*我們不是把使用者的話直接丟給 AI,而是先把它變成資料。*

## 第二幕・熱啟：成本模型（1.5 分鐘）

**操作**：在 Console 清掉前端快取（同上那一行），再輸入一次「日本」。

**指給對方看：**

- **視窗 B**：這次**沒有** Gemini 的日誌,只有一次資料庫讀取,`cached: true`。
- **視窗 D**：請求時間從 900ms 掉到 ~200ms。

> 「這張快取表是**全域共用**的——不是每個使用者一份。
> 全世界第一個查『日本』的人付了那 929 毫秒和那一次 LLM 呼叫,
> **之後所有人都是免費的**,直到 35 天後過期。
> 所以我們的邊際成本不是隨使用者成長,是隨**新目的地**成長。」

---

## 第三幕・兩層架構：使用者等的東西要最小（2 分鐘）

**操作**：繼續往下一步（縮圈頁）。

**指給對方看：**

- **視窗 B**：出現 `[destination-deep] ok { zones: 8, seasons: 12, keys: 12, ms: ... }`
- **視窗 C**：重新整理 → 多出一列 `deep:日本`。點開看 JSON:地帶卡組、12 個月的季節註記、關鍵詞、玩法標籤。

> 「這是**重層**。它的輸出比輕層大二十倍,所以我們**不讓使用者等它**——
> 它在使用者還在輸入目的地的時候就已經在背景跑了。
> 這是一個實測換來的教訓:我們原本把兩層合成一顆呼叫,結果入口頁要等**兩分鐘**,
> 因為使用者在等的是三頁之後才用得到的資料。**輸出長度就是等待時間。**」

（如果對方懂技術,可以補一句：`maxOutputTokens` 不是保險用的參數,它就是最壞情況的等待時間上限。）

## 第四幕・防呆與誠實（2 分鐘）

**操作 1**：輸入 `asdfgh`。

- **視窗 D**：**完全沒有請求**。
> 「亂打的字在瀏覽器裡就被攔下來了,一次 API 都不會發。
> 這是唯一一種『越多人亂打越省錢』的設計。」

**操作 2**：輸入「測試用」。

- **視窗 D**：有請求。**視窗 B**：`granularity: unknown`。
- **App**：畫面上出現**虛線圈**與琥珀色提醒,而不是實線金圈。
> 「模型說它不認識這個地方,我們就誠實畫一個虛線圈。
> 我們的原則是:**偵測可以不完美,但絕不無聲接受**——
> 使用者按下一步時還會再被攔一次,他必須親眼看見、親手放行。」

**操作 3**（可選）：按下一步 → 出現確認卡「有 1 個地方我查不到」。

## 收尾・三個數字（30 秒）

| | |
|---|---|
| **929 毫秒** | 一句「日本」變成結構化資料的時間 |
| **0 元** | 第二個查同一個目的地的人所花的 LLM 成本 |
| **0 次呼叫** | 使用者亂打時發出的 API 請求 |

> 「AI 在這個產品裡不是一個功能,是一條**管線**:
> 前面有防呆,中間有快取,後面有退位。
> 任何一層失敗,使用者都還是拿得到一個能用的畫面。」

## 附錄・示範用的 SQL

```sql
-- 最近寫進來的五筆（含格式化過的 JSON）
select query, created_at, jsonb_pretty(data) as data
from public.cached_destination_intel
order by created_at desc
limit 5;

-- 輕層／重層各有幾筆
select
  count(*) filter (where query like 'deep:%')     as 重層,
  count(*) filter (where query not like 'deep:%') as 輕層,
  count(*)                                        as 總計
from public.cached_destination_intel;

-- 這張表就是我們的「共用大腦」：列出目前累積了哪些目的地
select query, created_at from public.cached_destination_intel order by query;
```

## 附錄・如果對方問…

**「為什麼不用 OpenAI / 自架模型?」**
> 現階段是成本與延遲的取捨。這一層被包在 `ai-proxy` 後面,前端完全不知道背後是誰——
> 換模型只要改一個檔案的一個字串,前端一行都不用動。

**「資料會外流嗎?」**
> 送出去的只有目的地字串（例如「日本」）,沒有任何個人資料。
> 使用者的偏好我們的原則是「**學行為,不學內容**」——存聚合後的偏好向量,不存原始文字,
> 而且 RLS 保證只有本人讀得到、可以隨時清除。

**「AI 會亂編嗎?」**
> 會,所以我們假設它會。prompt 裡明講「寧可說不知道」,回來之後還有一層資料衛生:
> 顆粒度是 unknown 就清掉國碼與幣別,連國家都說不出來的也一律降級。
> **『不知道』永遠不能冒充『沒問題』。**
